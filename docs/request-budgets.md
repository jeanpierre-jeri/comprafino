# Public request budgets

The public web boundaries use explicit budgets without changing catalog eligibility, freshness, quantities, prices, matching, ranking or basket decisions. The policy lives in `apps/web/src/lib/public-request-policy.ts`; database transport configuration remains in `packages/db/src/client.ts`. These budgets limit an individual operation. They do not establish a global request rate, capacity guarantee or monetary spending cap.

## Implemented limits

| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- | -------------------------------------------------------------- | ----------------------------------------- |
| `/search`                              | 2–120 characters, known category can omit text, 30 visible products/page, page 1–2500; existing full-candidate safety limits | 15 s for the complete reader, including mapping; rendering follows      | 12 s per HTTP fetch; 10 s per SQL statement                    | `maxDuration = 30` s, including `after()` |
| `/products/[id]`                       | Valid public UUID, normalized mode, bounded history ranges                                                                   | 15 s comparison; independent 15 s history                               | 12 s fetch; 10 s statement                                     | 35 s for both stages and rendering        |
| `/listings/[id]`                       | Valid UUID and bounded history range                                                                                         | 15 s shared by listing and history reader                               | 12 s fetch; 10 s statement                                     | 20 s                                      |
| `POST /api/list/evaluate`              | 128 KiB actual/declared UTF-8 body; 50 items; existing field and catalog limits                                              | 15 s from handler entry, including body read, validation and evaluation | 12 s fetch; 10 s statement                                     | 20 s                                      |
| `GET/POST /api/list/sync`              | Session owner; POST exact Origin, JSON, 128 KiB, version/revision/item schemas                                               | 15 s including authentication and persistence                           | 12 s fetch; 10 s statement, also for scoped session resolution | 20 s                                      |
| Search demand recording after response | Existing discovery admission/retention and refresh-ID caps; no retailer HTTP                                                 | 10 s for the whole callback                                             | 10 s fetch; 8 s statement                                      | Included in search's 30 s                 |
| Evaluation and sync browser requests   | Existing Query/session keys and explicit mutation sequencing                                                                 | 20 s through response body parsing                                      | Server limits above                                            | Not a platform setting                    |

Reading a POST body has a separate **5 s** allowance inside its handler's overall budget. A stalled stream is canceled and returns 408 if this limit fires first. Oversized input remains 413; malformed JSON/schema remains 400. Invalid list data does not enter catalog evaluation. For sync, authentication still precedes body parsing.

The 15/12/10 s hierarchy uses the [03E HTTP evidence](history/catalog-http-performance-2026-10-16.md): approximately 9.53 s worst representative concurrent p95, 9.99 s maximum broad search, and 8.38 s maximum prolonged mixed basket at 50,000. The hierarchy leaves time for transport and application processing after SQL. It is a starting operational budget verified locally, not a deployed SLA. Product history retains an independent failure state and therefore an independent budget; the product page is not advertised as a 15 s complete-response guarantee.

An initial 5 s callback/3 s statement allowance for demand recording was too short in four concurrent broad searches at 50,000 listings: five measured responses and two warmups had failed background work despite valid foreground results. Its separate allowance was increased to 10/8 s, with 30 s declared for the search function. Benchmark summaries count SQL, transport and background failures separately from valid HTTP responses; a successful streamed page alone does not demonstrate successful demand recording.

## Cancellation and PostgreSQL

`createDatabase` accepts optional `requestTimeoutMs`, `statementTimeoutMs` and `signal`. Default callers outside these public boundaries retain their previous behavior. Each HTTP execution gets a fresh timeout signal combined with the request signal. An aborted request cannot start another fetch with that client; another request creates its own client and can recover. Sync authentication creates a scoped auth instance so a request signal cannot poison the shared singleton.

The effective statement limit is the smaller of the requested budget and any existing nonzero PostgreSQL timeout; a stricter configured limit is preserved. The statement limit is applied with `set_config('statement_timeout', ..., true)` **inside the same Neon HTTP transaction** as the original statements. This adds one small configuration statement to an existing batch, and wraps a direct query in a single HTTP transaction; it adds no separate HTTP round trip. Drizzle direct and batched results retain their original shape. No URL session-option assumption, global `ALTER ROLE`, migration or database-wide setting is used. Neon documents [non-interactive HTTP transactions](https://neon.com/docs/serverless/serverless-driver).

An HTTP timeout or disconnect is not proof of PostgreSQL cancellation or rollback. PostgreSQL's own [statement timeout](https://www.postgresql.org/docs/17/runtime-config-client.html#GUC-STATEMENT-TIMEOUT) bounds each statement, including lock waits. It does not bound the total of several statements in one batch. Current public foreground batches have one domain statement; discovery's lock and insert are two statements and can outlive the 10 s callback until the SQL budget stops them or they finish. A canceled transport can leave a successful write with a lost response. Tests explicitly wait for underlying SQL before dropping their owned schema.

`withinRequestBudget` propagates abort, bounds asynchronous waits even when a dependency ignores its signal, and rejects late results. It checks elapsed time after synchronous work, but JavaScript cannot preempt a synchronous CPU loop. It does not guarantee a hard wall-clock response limit under event-loop starvation. The hosting declaration is an outer guard; normal `next start` does not simulate a deployment function being killed. Server Components do not expose a request disconnect signal here: search and detail reads use their deadlines, while API handlers also consume `Request.signal`. `after()` has its own allowance because it starts after rendering, possibly following a disconnect.

## Recovery and uncertain writes

Evaluation failures return a safe uncached 503; search/detail pages use their existing recoverable error UI. A streamed search can already have HTTP 200 headers when its reader fails, so callers and tests must inspect the completed result. A history failure does not invent prices or recommendations.

Sync reads and failures before mutation entry return 503 `list_unavailable`. Once the mutation boundary has been entered, an unclassified failure returns 503 `mutation_uncertain`: the handler cannot infer rollback from a missing response. Known domain rejection remains 422; known revision exhaustion remains an unavailable 503 with no write. Existing 401/403/409/413/415 contracts remain. Safe diagnostics do not expose SQL, credentials, accounts or list content.

The browser never automatically retries a timed-out mutation. It keeps the last validated document in its session-scoped Query cache and retains anonymous storage, but withholds account recommendations and editing until a successful GET establishes current state. Late POST/body results cannot install data, clear anonymous storage or broadcast success. Focus refresh or explicit retry can perform that GET. Retrying anonymous import then uses the existing authoritative read and merge/CAS rules; it does not blindly resend the lost request. The existing single replay after a confirmed 409 remains bounded by the same browser operation budget.

## Refresh frequency and hosting verification

Evaluation retains its 60 s interval while visible, refresh on focus, no background interval, no automatic retries and no retention after the observer is removed. Pending or failed evaluations do not display old recommendations. Manual refresh joins an in-flight fetch instead of canceling it and starting another. A slower cadence or new stale cache could cross a freshness boundary, so neither is introduced.

The interval alone creates roughly up to 60 evaluations per hour for a continuously visible tab, before focus/list/mode changes; 100 such tabs would create roughly 6,000 per hour. This arithmetic is not measured production capacity. Four concurrent closed benchmark requests do not establish a safe sustained arrival rate. Client cadence is not a public rate limiter and can be bypassed by direct callers.

Vercel documents the App Router [named `maxDuration` export](https://vercel.com/docs/functions/configuring-functions/duration) and [managed WAF rate limiting](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting). The installed Next 16.3.8 docs were consulted before changing route declarations. The repository does not prove which plan, deployment settings, firewall rules or spending protections are enabled on the account. Absence of an in-code limiter is not evidence that external protection is absent. No deployment settings were changed.

Vercel's [request cancellation](https://vercel.com/docs/functions/functions-api-reference#cancel-requests) is opt-in through `supportsCancellation` and can terminate a matching function on disconnect, even without an abort listener. This repository does not declare that option. Local `Request.signal` tests therefore do not prove deployed disconnect propagation. Inspect the actual deployment first; assess read/evaluation routes separately from sync mutations and required `after()` work before proposing an opt-in. Do not apply a blanket cancellation glob as a routine timeout adjustment.

Before deployment, verify that these declarations appear in the target deployment, inspect existing managed rules and measure remote cold starts/transport. If aggregate frequency needs control, first evaluate the hosting provider's existing WAF in logging mode for these paths, then select limits from actual traffic and shared-IP behavior. Do not substitute a process-local Map for a global limit. No Redis, queue, new service, global concurrent-request gate or speculative retry mechanism is introduced.
