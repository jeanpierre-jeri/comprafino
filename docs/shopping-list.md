# Shopping lists

[Milestone 19B](shopping-list-persistence.md) adds backend remote-list capability for authenticated users. Milestone 19C imports anonymous localStorage lists into remote-authoritative account lists with newer-item selection and safe clearing. Missing-item remote removal is read-only after revision comparison; stale operations return 409 with current state.

Current domain guidance. Dated audits, measurements and acceptance narratives are preserved in [engineering history](history/engineering-notes-2026-10-05.md).

## Contextual creation and editing

Selecting **Agregar a mi lista** on a retailer card or listing detail saves that concrete retailer SKU through an optional `listingId`, its original label, package count and frequency. An independent listing can be preferred or strict without inventing a canonical identity. Canonical comparison pages still save their validated canonical product. Search-level **Agregar como necesidad** remains an explicit generic purchase; it alone normalizes supported families such as `huevos tottus` into `Huevos`.

The editor offers **Prefiero este producto** (with compatible alternatives) and **Solo quiero este producto** (same product only). It preserves the selected listing through edits, browser persistence, duplicate detection and authenticated synchronization. Different source SKUs do not merge just because they share a family or canonical group. Older generic records remain generic: their original SKU was never recorded, so recovering it requires selecting the desired product again. Existing exact canonical and legacy normalized quantities retain their semantics.

Evaluation resolves a listing's current validated canonical association and family from the catalog, never from saved metadata. Its selected-store quote remains the primary quote even if another store or product is cheaper. Revoked associations and two null canonical IDs cannot establish equality. Other-store exact matches need a currently safe canonical association. Substitutes need current source family and strong quantity evidence; whole packages fulfill the same amount. Invalid, stale, unavailable or missing source evidence cannot authorize substitutes or replace the row with a different product.

`/list` groups separate product cards by recurrence. Each shows the saved name, a catalog image with fallback, package count, current store, purchase total and a concise observed minimum when available. A labeled 44px edit button remains immediately accessible. One keyboard-accessible disclosure reveals the current purchase, price history, purchase timing, cheaper alternatives with images and removal. Alternatives identify the specific product, retailer, purchase savings, package count and any excess quantity. Conditions and unknown stock remain explicit. Refreshes and failures withhold prices, savings and advice together; no new client cache is added.

The basket summary is labeled **Plan de ahorro sugerido**, because it can use approved alternatives. It does not replace saved selections. Its existing plan and supermarket comparison dialogs retain the full fulfillment details. Generic rows explicitly explain that a product must be selected from its listing to track a specific SKU.

The shared dialogs retain focus containment/return, Escape/backdrop/close controls and reduced-motion behavior. Search ranking, public canonical matching gates and retailer access rules are unchanged.

## Observed minimum prices

The same read-only evaluation snapshot returns `priceHistories` for the displayed exact product and retailer, covering the last 7, 30 and 90 Lima calendar dates (including today). Each period reports the minimum ordinary PEN/UN sale-package price, most recent actual observation of that minimum, elapsed calendar days and number of dates with evidence. The UI compares this package minimum to today's ordinary **per-package** price, including in benefits mode and when buying multiple packages.

SQL samples actual daily first/last observations and recorded price-state changes within those observed intervals. Intraday changes can therefore contribute a known minimum, while KG, reference and conditional prices cannot. Days without observations stay absent. Canonical-only selections retain the association-date cutoff; directly saved SKUs use their own history without attributing it to a canonical product. Different retailers, substitutions and generic needs never share a history. Missing current source quotes withhold the comparison rather than attaching an alternative's history.

These are observed minima within bounded windows, not lifetime minima or forecasts. Sparse coverage is disclosed. The existing conservative weekday rule can recommend a day when its evidence gate passes; weekly/monthly windows support comparison with past prices but do not predict a future cheapest week/month. No chart, migration, dependency, retailer request or background collection is added.

## Current savings notices

The list shows a compact count of current savings opportunities. “Ver ahorros” expands the existing item links; selecting one opens the single product panel, scrolls and focuses the corresponding row. A brief opportunity amount remains visible on each qualifying row. Item callouts inside that detail distinguish an approved preferred alternative, the exact same canonical product in another retailer, and compatible generic fulfillment. The amount compares evaluated **purchase totals for the saved need**, with package counts and overbuy disclosed in the existing options. It is not a historic price drop, a sum of basket savings, a guarantee of stock or a future checkout price.

Notices require both at least S/ 1 and 5% savings against the stated baseline, reusing the existing preferred savings gate for display without changing eligibility, ranking or basket optimization. Generic notices compare the next evaluated option; tied cheapest offers suppress a claim rather than selecting a more expensive baseline. Strict/preferred same-product notices require the saved canonical identity and a different retailer. An unavailable preferred item may still show the existing safe alternative, but cannot support a savings claim without a valid baseline. CMR conditions on either side remain explicit.

Notices are derived from the existing validated evaluation response and refresh with prices. Pending/failed requests withhold them; they return after successful retry. There are no repeated toasts, browser-notification permissions, background delivery, new cache or persistence fields. The summary is a named region and item notices use a non-interrupting note role. Current source availability disclosures remain alongside each option.

## Weekday purchase advice

`/api/list/evaluate` now returns `weekdayRecommendations` alongside current prices and baskets, in the same read-only SQL snapshot. This advice always uses ordinary PEN/UN sale-package prices, including in benefits mode; it never combines CMR, reference prices or purchase totals across stores. No basket-wide optimal weekday or future saving is inferred.

The basket statement materializes five fields of open price states once in `current_prices`, reusing them for public identity, the complete current-catalog count, historical candidate admission and current offers. The open-state predicate runs once when building that relation; repeating it on the materialized result would reuse the full history's null fraction and underestimate current candidates. The shared identity and purchase predicates still apply separately. Listing JSON and benefits remain filtered before transport. Historical evidence continues to join the full `price_history` table, including closed intervals; the temporary price relation is scoped to one statement and is not a cache or persisted table. Search readers retain their existing direct price-history joins. This avoids repeated parallel hash joins in the basket without changing PostgreSQL settings or its container resources.

The internal basket rows retain the native listing UUID for the historical join and textual UUID ordering, plus the native retailer ID for family-category predicates. This preserves join statistics and avoids reconstructing listing JSON just to read a scalar key. Family predicates still use the same retailer-scoped categories and title hints, with core classification remaining authoritative. The output projection excludes both helpers: transported offers, canonical eligibility and history semantics remain the same. Equivalence tests compare against the previous JSON-based join, including association cutoffs and interrupted or conflicting price states.

Saved strict/preferred identities participate. Direct SKU selections use only that listing; canonical-only selections use their current safe exact-product candidates. A preference's substitute never inherits its pattern. Generic needs receive no recommendation: family compatibility alone does not establish that a single SKU's history represents a whole need. Series remain separate by listing/product and supermarket; no retailer pooling or cross-product aggregation occurs. Current eligibility, freshness and tri-state availability continue to apply. For canonical-only selections, daily evidence before the current association's `linked_at` is withheld to avoid assigning older coverage to an identity without association evidence.

The conservative engineering gate uses **the last four completed Monday–Sunday weeks in America/Lima**, excluding the partial current week. Each series must have all **28 real covered dates**, with positive ordinary PEN/UN prices recoverable at the day's actual last observation. Every state intersecting the interval between that day's actual first and last observations must have the same supported ordinary price. Reference-only transitions are allowed; intraday ordinary changes, unsupported states, missing states and missing dates withhold that day. Open states never generate dates. One real daily observation establishes a price sample, not continuous availability or a guaranteed all-day price.

A recommendation requires the **same unique minimum weekday in all four weeks**, at least **S/ 1 and 5% below every other day's ordinary price in each week** (percentage relative to that other day). This fixed prudence threshold is not a calibrated statistical confidence level. Complete constant prices, ties, small differences or inconsistent winners produce “No observamos un patrón claro para recomendar un día.” Incomplete or absent evidence produces **“Aún no hay suficiente historial para recomendar un día”**, including for generic needs. We do not select older favorable weeks, interpolate gaps, average intraday prices or multiply sample coverage by state duration.

The compact row shows a brief historical suggestion only when supported. The conservative fallback and “Fundamento del día sugerido” section live inside the same product detail panel, where dates, coverage, supermarket-specific suggestions, criterion and limitations are shown without a second disclosure. Pending/failed evaluations withhold advice along with prices. Multiple supermarkets can have different suggested days; the first displayed series follows current candidate order and is not a claim about the best store. No storage change, dependency, migration, cache or background collection was added.

The October 7 read-only audit found coverage from October 4–7, at most four covered dates per SKU; that dated sample could not pass this gate. Present-day eligibility needs current evidence and was not queried for the October 17 documentation reconciliation. See [the dated audit](history/weekday-coverage-2026-10-07.md) and [coverage semantics](price-history.md#observation-coverage-and-chart-choice).

## Desired quantity and sale-package counts

Generic `quantityMode: normalized` means the amount needed: 30 eggs, 5 kg rice or 3 L cooking oil. Strong catalog quantity evidence determines how many whole packages fulfill it. Mass/volume use integer thousandth-unit arithmetic; units are whole counts. Packages = ceiling(desired quantity / package quantity). Offers exceeding twice the desired amount are excluded.

New preferred/strict `quantityMode: packages` means whole **sale packages**, independently of their contained measure. Two exact 30-egg trays mean two trays, not two eggs. Two exact 1 kg rice packages mean two packages. Exact recommendations price that many sale packages without asking the user to enter the SKU's own size. Direct per-kg quotes cannot be treated as sale-package prices.

Preferred alternatives fulfill the contained amount of those requested packages using strong current exact-product quantity evidence. Two 30-egg trays may be compared with four safe 15-egg trays. Two 1 kg packages may be compared with four safe 500 g packages. If the current exact package contents cannot be established, alternatives are withheld. Options carry their own quantity unit, so mass/volume alternatives are not mislabeled as package counts.

Strict products retain their exact identity and never substitute; a selected listing can admit another retailer only through its current safe canonical association. Preferences retain their original identity and show an alternative only when it saves at least both S/ 1 and 5%, or when the preferred offer is unavailable and equivalent fulfillment can still be established. Exact eligibility, freshness, ordinary/conditional-price safeguards and matching rules remain unchanged.

## Browser storage and migration

The existing `comprafino-shopping-list` localStorage key now stores `{ version: 2, items: [...] }`. Items retain UUID, intent, label, query, quantity, frequency, timestamps and canonical reference. Optional `listingId` retains an exact retailer selection without a canonical identity. The same JSON document is accepted by account synchronization, with no SQL schema migration; all clients should reload after deployment to use the updated validator. Other fields include `quantityMode` and nullable `substitutionProfile`; generic creation stores a normalized query and a conservative inferred profile. The measure already captures normalized quantity dimension. Unsupported needs are saved with a null profile and receive no automatic substitutions.

Valid version-one lists migrate in memory to version two on read. All three intents, IDs, canonical references, custom labels, original quantities, frequency and timestamps are retained. Generic profiles are inferred only through the conservative domain policy. Legacy exact quantities stay `normalized`: storage has insufficient package evidence to reinterpret 30 eggs as 30 trays or 2 kg as two packages. Their editor explicitly explains that the original measure is retained. Legacy exact unit counts for mass/volume still preserve Milestone 15's container-count behavior. Re-adding the SKU creates an explicit package-count item; the two quantity modes have distinct duplicate keys.

A subsequent explicit write serializes version two. Reading does not overwrite the original stored value. Invalid JSON/schema, duplicates or unknown versions recover to an empty list with a message; malformed input is not silently coerced. Schema defaults preserve omitted legacy metadata conservatively. Browser storage failures retain session state and explain reload loss. Limits remain 50 needs, whole counts and up to three kg/L decimals. Cross-tab updates, deletion and last-writer-wins behavior are unchanged. Migration affects browser data only; there is no SQL migration.

## Compatibility and current prices

Search relevance and substitution compatibility are separate. Broad search can include quail eggs, specialty rice/oils and mixed detergent forms. Saved needs cannot use keyword relevance as evidence of equivalence. Framework-independent APIs and family policies are documented in [substitution compatibility](substitution-compatibility.md).

Evaluation reuses normalized family/category and strong quantity evidence. Independent normalized retailer offers can satisfy generic needs without gaining invented canonical/history associations. Exact associations still require current automatic high-confidence public matching eligibility. Null or inconsistent saved compatibility fails closed. Preferred compatibility comes from the current canonical product, never a custom local label. A negative source-family classification remains negative.

Shopping lists remain browser-local (with a session fallback). Evaluation requests transiently send list labels, queries, amounts and item metadata to the server. Evaluation does not persist the list or create discovery demand; no account/IP identity is attached.

[Milestone 19A authentication](auth.md) does not change these boundaries. `/list` and `/api/list/evaluate` remain public. Milestone 19C adds remote-authoritative authenticated lists, anonymous import and safe logout/account transitions. See [synchronization behavior](shopping-list-persistence.md#client-synchronization-19c).

`/api/list/evaluate` accepts at most **128 KiB of UTF-8 body bytes**, including JSON escaping. This accommodates 50 items with maximum label/query/profile fields and conservative metadata headroom. Both declared length and actual streamed bytes are checked before JSON parsing; no streaming JSON parser is used. Oversized bodies return safe 413, malformed JSON/schema or more than 50 items return 400, and rejected requests never access market evaluation. Within the byte cap, labels/queries remain limited to 120 characters.

`/api/list/evaluate` validates the version-two list and performs read-only current-catalog queries; evaluation never ingests or refreshes retailers. The unused legacy `GET /api/list/products` endpoint was removed in the final repository cleanup and now returns 404; dialogs use contextual creation and do not search that endpoint. Responses are uncached and validated; list prices refresh on tab return and every minute. Fresh active ordinary prices and supported CMR benefits use existing ranking. Milestone 16 now compares optimized complete/partial baskets for up to one, two and three retailers; per-item recommendations retain their existing behavior. Frequencies do not produce a monthly recurring bill.

## Limits and current basket work

Basket optimization consumes shared approved fulfillment options and preserves substitution, freshness and quantity gates. Broad search relevance cannot establish equivalence. Legacy exact normalized quantities are retained; family coverage is limited, names may under-describe specialty properties, canonical references can become unavailable, and signed-out lists have no remote backup. See [basket optimization](basket-optimization.md).

## Transient browser-storage failure (Cleanup A)

Storage rereads use the latest provider/session list as their fallback when localStorage access throws. Mutations and storage-event handling preserve that list instead of replacing it with an empty list. A read warning survives the same mutation even if its subsequent write succeeds. The root Zustand provider keeps session state across client navigation; a full reload without working storage cannot recover an unpersisted session.

Working storage still supplies the latest persisted state before mutation and cross-tab events still synchronize it, including removal/clear. Missing or malformed/incompatible stored data retains the existing empty-list recovery semantics; it is distinct from inaccessible storage. No state-management dependency was added.

Current item and basket responses are rendered only for the list object, price mode and refresh revision that produced them. When an item is removed or edited, the previous response is withheld immediately during rendering, before effects start reevaluation. This prevents a deleted item's basket assignment from being rendered against the updated list and preserves the remaining session items.

Public evaluation has a 15 s operation budget, 12 s DB fetch budget and 10 s SQL statement limit; body reads are bounded to 5 s and browser evaluation to 20 s. The 60 s visible-tab/focus refresh policy remains. A pending/failed refresh hides recommendations; manual refresh joins an in-flight fetch. See [public request budgets and recovery](request-budgets.md).
